# 工具读取的写法

本页是检查工具解析的每种固定写法的权威正文：写在哪里、怎么写、可以用哪些值。复制 `scripts/wiki/` 时本页随工具一起复制，所以接入项目里的模板和 `AGENTS.md` 只写摘要，格式以本页为准。规则名、配置字段和工具发现问题后怎样报告，见[配置与规则](reference.md)。

工具只读这几行固定格式，其余正文按普通 Markdown 处理，不要求 frontmatter。这些行在渲染后的页面上就是一句普通的话，人可以直接读懂。

## 通用约定

- 每个关键词和每个取值都有一个中文写法和一个英文写法。英文不区分大小写。冒号可以写全角"："或半角":"。
- 代码块和行内代码里的内容不解析，所以格式说明里可以用反引号举例。
- 人和 Agent 统一写成 `human:<名字>` 或 `agent:<名字>`，用在核对人、问题作者、负责人和签收人上。Agent 只能把自己写成 `agent:`。工具分不出一行是谁写的，所以配置了 `remind` 的项目里，暂存的改动新增了 `human:` 名字时，提交提醒会请提交者向用户确认。
- 项目可以在 `docs/wiki.json` 的 `status_values` 里给计划、决策记录和待处理项补充同义状态。需求状态、审查判定和关键词不能配置。

## 关键词

| 中文 | English | 写在哪里 | 例子 |
|---|---|---|---|
| `状态` | `Status` | 计划、决策记录、审查 README 和待处理项写在一级标题下第一个非空行；需求写在编号标题下第一个非空行；审查问题写在问题标题下第一个非空行 | `状态：执行中。范围：notes。` |
| `负责` | `Owner` | 计划或审查 README 的状态行里 | `负责：agent:kiro。` |
| `核对` | `Verified` | 知识页一级标题下、第一个二级标题之前，在行首 | `核对：agent:kiro，2026-10-28；human:clarence，2026-11-02。` |
| `复核期限` | `Review by` | 和核对行在同一区域，可以接在核对行后，也可以单独一行 | `复核期限：2027-04-28。` |
| `人工验证` | `manual` | 需求验收条目的末尾，写在括号里 | `（人工验证）` |
| `验收核对` | `Acceptance check` | 需求文件里，标了人工验证的验收条目下一行，在行首 | `验收核对：PW-01.1，agent:codex，2026-10-29。` |
| `证据` | `Evidence` | 需求条目里，在行首，后面至少有一个链接 | `证据：[行为测试](../tests/test_title.py)。` |
| `覆盖需求` | `Requirements` | 计划里，在行首 | `覆盖需求：PW-11、PW-12。` |
| `覆盖问题` | `Covers` | 审查目录的 `plan-<主题>.md` 里，在行首 | `覆盖问题：r01-1、r02-3。` |
| `作者` | `Author` | 审查问题小节里，通常写在"观察"旁 | `（作者：agent:a，2026-10-28）` |
| `核对` | `Verification` | 审查问题小节里单独一行，可以加粗，下面紧跟核对表 | `**核对**` |
| `判定` | `Verdict` | 审查核对表的第三列表头 | 表头依次写轮次、核对人、判定、依据 |
| `方案` | `Plan` | 审查问题小节里，在行首，可以加粗 | `**方案**` |

设计文档写的 `对应需求：PW-11` 和正文开头的 `范围：…` 是给读者的约定，工具不解析这两行本身；需求编号在任何现行文档里出现都算引用。

## 计划、决策记录和待处理项的状态行

一级标题下第一个非空行写 `状态：<值>。`，后面可以接范围、负责人等说明。工具只读这一行，不读 frontmatter、路线图勾选或步骤清单。

```markdown
# 多行标题支持

状态：执行中。范围：notes。负责：agent:kiro。
```

| 中文 | English | 类别 | 含义 |
|---|---|---|---|
| `草案` | `draft` | draft | 尚未生效 |
| `执行中` | `active` | active | 工作正在进行 |
| `阻塞` | `blocked` | blocked | 工作暂停，等待条件 |
| `当前有效` | `current` | current | 决定现行有效 |
| `已完成` | `finished` | finished | 工作已经结束，可以归档 |
| `被替代` | `superseded` | superseded | 已有替代文档 |
| `废止` | `retired` | retired | 不再适用，没有替代 |
| `待分诊` | `open` | open | 待处理项还没有结论 |

项目自己的写法，例如"已取消""采用"，在 `status_values` 里映射到上面的类别：`{"已取消": "finished", "采用": "current"}`。

负责人写在状态行里，格式是 `负责：human:<名字>` 或 `负责：agent:<名字>`，多人或多个 Agent 同时工作时必写。

## 核对行与复核期限

知识页在一级标题下、第一个二级标题之前写：

```markdown
# 标题校验失败的处理

核对：agent:kiro，2026-10-28；human:clarence，2026-11-02。复核期限：2027-04-28。
```

- 每次核对是一条"核对人，YYYY-MM-DD"，多条用"；"分隔。再次核对时在行尾追加一条，不删旧记录。
- 复核期限是绝对日期，只给会过期的页面写，例如运维手册、外部事实和调查结论；不能早于最近一次核对。
- 只有以 `核对：` 或 `复核期限：` 开头的行才算，列表项和说明文字里提到这两个词不解析。

## 需求条目

```markdown
### PW-11 提交时提醒同步文档

状态：已实现。

- PW-11.1 只改代码的提交给出 docs-not-updated 提醒。
- PW-11.2 规范读起来清楚。（人工验证）
  验收核对：PW-11.2，agent:codex，2026-10-29。

证据：[行为测试](../tests/test_wiki.py)。
```

- 每条需求是一个二级到四级标题，标题以编号开头。默认编号是"大写字母开头的前缀、短横线、数字"，例如 `PW-11`；已有编号用别的格式时，在 `requirements.id_pattern` 里登记，不改编号。
- 标题下第一个非空行是状态，取值见下表。
- 验收条目是以"需求编号.数字"开头的列表项，例如 `PW-11.1`。测试在说明文字里写这个编号，就算引用了它。
- 不能由命令证明的条目在末尾标"（人工验证）"，下一行写 `验收核对：<验收编号>，<核对人>，YYYY-MM-DD。`。验收核对只对标了人工验证的条目有效：写在其他条目下，工具会给出警告，这一行也不能代替测试。
- 状态改为已验证时，写一行"证据："并链接到测试或验证记录。
- 计划写"覆盖需求："列出编号；维护类工作写 `覆盖需求：无（<原因>）`。需求取消时状态改为已废止，不删除编号。

| 中文 | English | 含义 |
|---|---|---|
| `提出` | `proposed` | 正在讨论，边界和验收还没确定 |
| `已接受` | `accepted` | 项目接受这个目标，还没实现 |
| `已实现` | `implemented` | 实现已经完成 |
| `已验证` | `verified` | 有测试或核对记录作为证据 |
| `已废止` | `retired` | 不再要求，编号保留 |

## 审查问题

一次审查是一个目录 `dev/reviews/<开始日期>-<主题>/`，里面有 `README.md` 和每一路一个分路文件；跨多条问题的修复写在同目录的 `plan-<主题>.md`。目录名以开始日期开头，因为同一主题会多次审查，按日期能找到最近一次；这个日期之后不再改。

每条问题是分路文件里的一个二级标题，标题以问题编号开头，编号是"路号-序号"，例如 `## r01-1 只含零宽空格的标题会通过校验`。标题下第一个非空行是判定：

| 中文 | English | 含义 |
|---|---|---|
| `待核对` | `pending` | 还没有人核对 |
| `成立` | `confirmed` | 问题成立，需要方案 |
| `收窄` | `narrowed` | 部分成立，写清哪部分不成立 |
| `不成立` | `rejected` | 问题不成立 |
| `已知` | `known` | 已有方案、缺口或决策，必须链接过去 |
| `重复` | `duplicate` | 和本次审查里另一条重复，必须写出那个编号 |

小节里依次写观察（带作者）、推测（可省略）、核对表、方案和签收。核对表每轮一行，四列依次是轮次、核对人、判定、依据；核对人不能是作者。核对完成后，把小节开头的判定改成最后一轮的判定。签收写"签""签（收窄）"或"不签"，以及签收人和日期；工具不解析签收。

## 待处理项

一条一文件，放在 `dev/inbox/<类型>/<主题>.md`，例如 `dev/inbox/bug/combining-character-count.md`。标题下第一个非空行写状态：

- 新建时写 `状态：待分诊。`，后面接来源。
- 处理完时写清去向（转成了哪份计划、写回了哪篇知识、和哪条重复，或者不处理的理由），状态改为 `状态：已完成。`，然后用 `archive` 归档。归档后，同名的新条目在 `check-new` 时会提示这段历史。

## 编号怎样分配

- **需求编号**取当前最大编号加一，用过的编号不再分配给别的需求。两个分支同时新增需求时可能取到同一个编号，合并后 `check` 报 `trace-duplicate-id`。这时后合并的一方改用下一个空号，并在同一次改动中改掉本分支里引用它的设计、计划和测试。已经合并进主分支的编号不改。会持续很久的并行分支，可以先单独提交一个只有编号标题和 `状态：提出。` 的条目，把编号占住。
- **审查路号**由负责汇总的人在审查 README 的分路表里分配，中途追加的路也先登记再开始写，各路执行者不自己取号。问题序号由每一路的执行者在自己的文件里顺序编写，不会和别的路冲突。
- 计划、决策记录和待处理项不编号，用描述主题的文件名，避免多人争用同一个顺序号。
